# Refine Skill

## Purpose

Loop review → triage → apply until the codebase stops yielding behavior-preserving
findings, then check it against the standards library once. The goal is
optimization and refinement: correctness of internals, performance, simplification,
dead code, duplication, docs that drift from the code. It is **not** a tool for
changing what the software produces for its user, even when a finding says that
output is wrong.

Sub-agents do the heavy lifting (reviews, fixes). The orchestrating agent — the one
reading this — owns one judgment no sub-agent makes for it: **whether a finding
changes behavior.**

The whole run is non-interactive. Never ask the user anything between start and the
final report, and never let a sub-agent ask. Every decision point below has a
default; take it.

## What "behavior" means here

**Behavior is what the software produces for its user, and the code is its
definition.** What the code does today is the contract — not the docs, not the
specs, not the tests.

- **A behavior change is a user-facing functional change:** given the same inputs,
  the software produces a different result — UI content, CLI output, exit codes,
  messages shown, files written and their formats, network calls and other side
  effects on the user's system, what is shown or hidden and when.
- **Faster is not a behavior change.** Using less time, memory or I/O improves the
  user's experience without changing what the software produces. The exception is
  where timing *is* the output: timeouts, schedules, poll intervals, debounces, rate
  limits, expiry windows. Changing those is a behavior change.
- **Internal-only changes are allowed** when the result is functionally the same:
  refactors, dead-code removal, de-duplication, internal error handling that ends in
  the same visible outcome, internal names and structure.
- **The project's docs, specs, comments and CLAUDE.md that contradict the code are
  fixed to match the code.** Code wins. A finding that says "code violates
  documented rule X" is resolved by correcting the project's document, never the
  code.
- **Tests are not the arbiter.** Tests exercise internals as well as behavior, so a
  test that must change is neither proof of a behavior change nor proof of its
  absence. Judge from the code.
- **Security and correctness fixes that change behavior are still behavior changes.**
  Defer them and report them prominently; do not apply them.

This is judgment, not a deterministic check. When a fix is ambiguous — part
internal, part user-facing — defer it. A deferred finding costs the user a read; a
wrongly applied one costs them a regression they did not ask for.

## Flow

1. Setup
2. Iterate, up to `--max-iterations`: Review → Triage → Apply → Convergence check
3. Standards: one `jewzaam-reviews:standards` pass → Triage → Apply
4. Final report

Every sub-agent is started in the background; the host wakes the orchestrator when
it finishes. Never wait on a sub-agent in the foreground or sleep-poll for one.

## 1. Setup

- `<PLUGIN_ROOT>` is two directories above this `SKILL.md` (this file's own
  location; `${CLAUDE_PLUGIN_ROOT}` where the host sets it).
- How sub-agents run this plugin's skills:
  - `jewzaam-reviews:review` and `jewzaam-reviews:standards` set
    `disable-model-invocation`, so their sub-agent reads
    `<PLUGIN_ROOT>/skills/<name>/SKILL.md` and follows it.
  - `jewzaam-reviews:apply-review` is invoked as a skill where the host allows it;
    otherwise its sub-agent reads the `SKILL.md` and follows it.
  - A followed `SKILL.md` with `` !`command` `` pre-fetch lines
    (`jewzaam-reviews:apply-review`, `jewzaam-reviews:standards`) has each of those
    commands run by hand, with `<PLUGIN_ROOT>` substituted for
    `${CLAUDE_PLUGIN_ROOT}` and `$ARGUMENTS` empty.
- Parse arguments: `--max-iterations N` (default 3); everything else is guidance.
- Run the project's full validation: its `check` target if it has one, otherwise
  every check, test and lint target it defines. If anything fails, report the
  failures and stop. With no validation at all, record that and continue. A green
  start is what lets every later failure be read as a regression from this run.
- Write an intent file in your scratch directory (never the project): the user's
  guidance verbatim, then the "What 'behavior' means here" section of this file
  verbatim. Reviews then rate findings knowing the run is behavior-preserving.

## 2. Iterate

### Review (sub-agents in parallel)

Every iteration runs **`jewzaam-reviews:review`**. Its sub-agent follows
`<PLUGIN_ROOT>/skills/review/SKILL.md` with these overrides:

- **Arguments** (Step 1): `--validate-buckets critical,important,suggestion,needs-review`
  followed by the guidance text
  `iteration <N>: full codebase refinement; uncommitted changes are prior refinement passes, judge the tree as it stands; pre-existing defects are in scope`.
  The guidance is plain trailing text, not a flag. It must begin `iteration <N>:`
  because the scope slug is the first 12 characters of the lowercased, hyphenated
  guidance — that gives each iteration its own `Findings-review-iteration-<N>*`
  files. `needs-review` is in the buckets so that findings a validator rescores
  upward reach triage.
- **Intent** (Step 2): the intent is the refine intent file; pass
  `--intent-file <intent file>` on every orchestrator call and gather nothing else.
- **Profile** (Step 4): ask nothing. If lens selection prints a `profile-hint: docs`
  line, add `--profile docs` to the review command — on a docs-only repo the code
  profile keeps every doc finding a suggestion.
- **Return** the cost table verbatim in its reply: `.tmp-review/costs.json` is wiped
  by the next review. The run report also survives in
  `Findings-review-iteration-<N>.md`.

Plus, when the session lists them:

- **Iteration 1 — `ponytail:ponytail-audit`** over the whole repo.
- **Iterations 2+ — `code-review high` and `security-review`** over the cumulative
  uncommitted changes, tracked and untracked. Never with `--fix` or `--comment`.
  This is what catches regressions the apply passes introduced; a full-codebase
  review spreads its attention over the whole repo and reports far fewer of them.
  Neither has anything to read on the unchanged tree of iteration 1.

These run in parallel with `jewzaam-reviews:review` despite its rule against running
other commands during a review: they are read-only apart from their own report,
which the review never reads. Skills outside this plugin are not bound by its
conventions, so their sub-agents are told: read-only except the report, no git
writes, no questions, throwaway repos only in the scratch directory. Each writes
`Review-<skill>-iteration-<N>.md` at the project root — numbered findings with
severity, `file:line`, issue, failure scenario, fix — after adversarially verifying
each finding by reading the code and tracing a concrete failure. Never `Findings-*`:
that prefix belongs to this plugin's renderers. Record a listed skill that was
absent in the final report.

**Re-judge `pre_existing` removals.** On a dirty tree, `jewzaam-reviews:review`
validators can drop findings because the defect predates the uncommitted changes —
not a verdict on the finding, and in a full-codebase run those are in scope. In
`issues[]` of `Findings-review-iteration-<N>.json`, every `finding_removed` entry
whose message starts `validator_removed[pre_existing]` names a `content_hash` in
parentheses. Before the next review wipes `.tmp-review/`, have a sub-agent judge
each one on its merits from `.tmp-review/10-merged/<content_hash>.json`. Survivors
go through triage like any finding; having no ID in the findings file, the apply
ones are applied by hand on the `Review-*.md` path.

### Triage (orchestrator, not delegated)

For every validated finding across all sources, every severity (skip findings still
in `needs-review`), read the cited code and decide:

- **apply** — behavior-preserving per the definition above, or a doc fix that aligns
  a project document with the code.
- **defer** — the fix changes behavior. Record why in one line.
- **skip** — not real, already fixed by an earlier apply in this run, or contradicts a
  decision the project records (its CLAUDE.md / design docs) where the code agrees
  with that decision. Record why.

Keep the defer and skip decisions across iterations. A later review re-reports the
same defect under a new title, new line numbers and a new `content_hash`, so match
by same file, overlapping lines and same underlying issue, judged by reading both
findings. A match gets the earlier decision without re-reading the code.

### Apply (one sub-agent per source, sequential)

Sources edit the same files, so never run two apply sub-agents at once. Each one:

- runs `jewzaam-reviews:apply-review` on its `Findings-*.json` with exactly the
  **apply** IDs as arguments (`<file> C0 I2 ...`), in batch mode from the start:
  no commits, outcome `pending-commit`. For a `Review-*.md` source it follows the
  same discipline by hand and appends an `## Apply outcomes` section;
- is given the "What 'behavior' means here" section verbatim;
- takes every `jewzaam-reviews:apply-review` question point without asking:
  - a failing Step 0 baseline means stop and report;
  - `severity: "error"` entries in the findings file's `issues[]` are recorded and
    the run proceeds;
  - a finding found invalid or already fixed is skipped with the reason recorded;
  - a finding that needs investigation is investigated, then applied or skipped;
- ignores `jewzaam-reviews:apply-review`'s "if the fix changes behavior, update
  affected tests" — a fix that would change behavior is not applied; it is skipped
  with the reason "changes behavior";
- never runs `git add`, `commit`, `stash`, `checkout`, `reset`, or switches branches;
- ends with the project's full validation green, and copies
  `Report-apply-review.json` to `Report-apply-review-<source>-iteration-<N>.json`,
  since every apply run overwrites the fixed-name report.

The tree is already dirty from earlier applies and staging is off-limits, so take
each source's delta by snapshot. Before its apply sub-agent, write to the scratch
directory `git diff` plus, for each untracked file,
`git diff --no-index /dev/null <file>`; after it, write the same again and
`diff -u` the before and after. Read that delta. Any user-facing behavior change in
it is a failure of this skill: have a sub-agent revert exactly that change, move the
finding to **defer**, and re-run validation.

### Convergence check

Converged when an iteration's triage yields **zero apply-able findings of any
severity** and validation is green. Severity is not a proxy for "worth doing": a
docs-only repo may produce nothing but suggestions. Otherwise start the next
iteration, until `--max-iterations`. Hitting the cap is not convergence — report it
as such, with the count of apply-able findings the last iteration still had.

## 3. Standards

Once, after the loop ends (converged or capped), a sub-agent runs
`jewzaam-reviews:standards`, which validates its own findings. On
`NOT_APPLICABLE` it asks nothing: the pass is skipped and the reason goes in the
final report.

Every standards finding reads "the code departs from standard X". The standards
library is not a project document and is never edited, so these findings get only
the ordinary test: apply when the fix is behavior-preserving, otherwise defer or
skip. Triage them as above, carrying the decisions already made, then apply the
**apply** IDs with one `jewzaam-reviews:apply-review` sub-agent, delta check
included. No further iteration follows.

## 4. Final report

Relay, without writing a new file (this plugin's renderers own `Findings-*` and
`Report-*`):

- iterations run and whether the loop converged or hit the cap;
- per iteration, and for the standards pass: validated counts by severity per
  source, applied / deferred / skipped;
- **every deferred finding** — file, ID, title, why it changes behavior; security
  ones first;
- final validation result, `git diff --shortstat`, and the count and line total of
  new untracked files;
- the cost tables the `jewzaam-reviews:review` sub-agents returned (relay as
  printed; never estimate).

Everything is left uncommitted for the user.

## Critical Rules

- Never ask the user anything during the run.
- Never apply a behavior-changing fix, whatever its severity.
- Never commit, stage, stash, or change branches.
- Never write or edit `Findings-*` or `Report-*` files by hand.
- Never wait on a sub-agent in the foreground.
